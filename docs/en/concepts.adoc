== Concepts

The format provides general information on the traffic situation on the road network of the Czech Republic:
accidents, obstructions, queues, closures and restrictions, roadworks, road operator actions and the
effects of weather on road conditions.

Closures and restrictions are also published separately in the `cz-ndic_d2-restrictions` format,
which is a subset of this format. Parking occupancy is not part of the format (see the
`cz-ndic_d2-city-parking-*` formats), nor is any status information (e.g. FCD speeds, see
`cz-ndic_d2-fcd-status`).

The format is based on the DATEX II publication `SituationPublication` <<EN16157-3>>. It uses the DATEX II 3.7 model without national extensions.

[[obalka]]
=== Envelope and publication header

Each message is a DATEX II 3 document with the root element `d2:payload`. The `xsi:type` attribute of the root element
specifies the publication type (here `sit:SituationPublication`), the `modelBaseVersion="3"` attribute
the model version and the `lang` attribute the default language of texts.

The format the message conforms to is identified solely by attributes of the root element:

[horizontal]
`profileName`:: format identifier without version (`cz-ndic_d2-common`),
`profileVersion`:: format version (`2.0`).

The publication header contains:

* `feedType` – identifier of the data source (distribution) in the register of the national access point
  <<nap>>. The source refers to the format in which it provides the data; the format of the message is
  identified by the `profileName` and `profileVersion` attributes. The `feedDescription` element is not used.
* `publicationTime` – time the publication content was created. If the content has not changed since
  the previous publication, the original time is kept; a new time is set only when the content changes.
* `publicationCreator` – publication provider: country code in lower case (`cz`) and provider
  abbreviation (`nationalIdentifier`).
* `headerInformation` – handling of the information; NDIC always sets `confidentiality` =
  `noRestriction` and `informationStatus` = `real`.

All times in the message include the time zone.

=== Situations and situation records

Each event is described by a `situation` element with a unique identifier (`@id`). A situation may evolve
over time; it contains the time of its last change `situationVersionTime` and the `headerInformation`
header.

[source,xml]
----
include::{samplesdir}/accident.xml[tag=situation-head,indent=0]
  ...
</sit:situation>
----

The information itself is carried by `situationRecord` records. A situation may contain several records,
each of a different type (`xsi:type`) – typically a cause (e.g. an accident) and its consequence (e.g. a
road closure). The record identifier is derived from the situation identifier and the record type.

[[verzovani]]
==== Versioning

* Each record carries a version number (`@version`), the creation time of its first version
  `situationRecordCreationTime` and the creation time of the current version
  `situationRecordVersionTime`.
* Each change of a record increases its version by one and changes `situationRecordVersionTime`.
* In version 3 of the model a situation has no version number. Its version is expressed by
  `situationVersionTime`, which always equals the latest `situationRecordVersionTime` of its records – each
  change of a record is therefore also a new version of the situation.

* `probabilityOfOccurrence` – `certain` for an event that has occurred, `probable` for a probable event,
  `riskOf` for a planned event that has not occurred yet.
* `safetyRelatedMessage` – `true` marks safety-related traffic information according to Commission
  Delegated Regulation (EU) No 886/2013 (SRTI).
* `source` – who created the information and is responsible for its correctness (`sourceIdentification`,
  where applicable `sourceName`).
* `generalPublicComment` – free-text description of the event by its originator, usually in Czech.
* `urlLink` – link to a web page with details of the event (`urlLinkType` = `html`).

NOTE: The situation summary record (`situationSummary`) offered by model 3.7 is not used yet: a summary
must have its own location, validity and mandatory type elements, which would make messages longer.
Comments remain in the individual records.

[[typy]]
=== Record types

The record type (`xsi:type` of the `situationRecord` element) specifies what happened. The format uses
these types:

[cols="2,3",options="header"]
|===
|Area |Record types
|Traffic flow (queues, heavy traffic) |`AbnormalTraffic`
|Accidents |`Accident`
|Obstructions |`VehicleObstruction`, `GeneralObstruction`, `AnimalPresenceObstruction`,
`EnvironmentalObstruction`, `InfrastructureDamageObstruction`
|Activities |`PublicEvent`, `DisturbanceActivity`, `AuthorityOperation`
|Driving conditions |`WeatherRelatedRoadConditions` (road surface conditions due to weather),
`NonWeatherRelatedRoadConditions` (sand, oil, spilled load), `PoorEnvironmentConditions` (precipitation,
visibility, wind, temperature)
|Roadworks |`ConstructionWorks`, `MaintenanceWorks`
|Traffic management |`RoadOrCarriagewayOrLaneManagement` (closures, changes of layout), `ReroutingManagement`
(diversions), `SpeedManagement` (speed limits), `WinterDrivingManagement`, `GeneralNetworkManagement`,
`GeneralInstructionOrMessageToRoadUsers`
|Services and equipment |`EquipmentOrSystemFault`, `RoadOperatorServiceDisruption`, `ServiceDisruption`,
`RoadsideAssistance`, `TransitInformation`
|Other |`Conditions` (general driving conditions)
|===

The profile contains the model elements published by NDIC and, in addition, diversions
(`ReroutingManagement`) and temporary speed limits (`SpeedManagement.temporarySpeedLimit`).

An accident with a spillage (fuel, oil, chemicals) is published as two records: `Accident`
and `GeneralObstruction` with `obstructionType` = `spillageOnTheRoad`. Wind speed is given in m/s.

[[platnost]]
=== Validity

Validity is given for each situation record separately in the `validity` structure. Only
`validityStatus` = `definedByValidityTimeSpec` is used, with the interval `validityTimeSpecification`
(class `OverallPeriod`) with the start `overallStartTime` and the end `overallEndTime`.

If an event applies only in a certain part of the day (e.g. works only during the day, at night or
outside rush hours), the interval is supplemented by the `validPeriod` element: the period name
`periodName` and the daily time period `recurringTimePeriodOfDay` (`startTimeOfPeriod`,
`endTimeOfPeriod`). Other recurring intervals (days of the week, dates) are not used; a recurring event is
otherwise described by several consecutive records. The validity interval may lie in the past, the present
or the future.

[[polohy]]
== Location referencing

The location is described directly in the message by the `locationReference` element, usually of type
`loc:SingleRoadLinearLocation` (linear location on a single road). A linear location is also used for
point-like events (e.g. an accident): in ALERT-C the primary and secondary locations are identical, OpenLR
and the Global Network sections describe a short road section at the place of the event. If the source
gives the location as a point, `loc:PointLocation` is used (ALERT-C `alertCPoint` of type
`AlertCMethod2Point`). Area locations are not used.

A location is usually described by several methods at the same time, depending on their availability at
the given place; all of them describe the same real-world section. At least one method must be given. All methods are part of the DATEX II 3.7 model.

[cols="2,3,4",options="header"]
|===
|Method |Element |Use
|ALERT-C |`alertCLinear` (`AlertCMethod2Linear`) |where a location exists in the ALERT-C location table
|OpenLR |`openlrLinear` |always, where the location can be encoded (dynamic location referencing)
|Road chainage |`linearWithinLinearElement` with `roadNumber` |roads with chainage
|Global Network |`linearWithinLinearElement` with `LinearElementByCode` |sections of the Global Network (ŘSD)
|Location path |`gmlLineString` |line in WGS-84 for display on a map (<<prubeh>>)
|===

=== ALERT-C location referencing

The method describes a linear location by codes of the ALERT-C location table <<ISO14819-3>> in the
`alertCLinear` element of type `AlertCMethod2Linear` (a point location similarly by `alertCPoint` of type
`AlertCMethod2Point`).

* The location table is identified by `alertCLocationCountryCode`, `alertCLocationTableNumber`
  and `alertCLocationTableVersion`. The country code is given according to IEC 62106 – for the Czech
  Republic the value `2` (not `CZ`).
* According to the ALERT-C principle, the primary location (`alertCMethod2PrimaryPointLocation`) is the
  place where the event occurred or where the driver leaves the problem section; the secondary location
  (`alertCMethod2SecondaryPointLocation`) is the end of the queue or the place where the driver enters the
  problem section.
* `alertCDirectionCoded` = `positive` if the direction of traffic matches the coding direction of the road
  in the location table.
* `alertCAffectedDirection` (mandatory) specifies which directions of traffic the event
  concerns, relative to the direction of the described location (given by `alertCDirectionCoded`):
  `aligned` for one-directional events in this direction, `both` for events valid in both directions.
* Long events that cannot be described by one ALERT-C path have several `alertCLinear` elements.
* A point-like event (including the inside of a junction or tunnel) has identical primary and secondary
  locations.

IMPORTANT: The meaning of `alertCDirectionCoded` is the opposite of the meaning of the RDS-TMC
`direction` bit, which is used to find the secondary location.

=== OpenLR location referencing

The OpenLR method (`openlrLinear` element) describes the location independently of any map: the
subscriber finds it in its own map by searching a route (so-called on-the-fly location referencing). The
reference points `openlrLocationReferencePoint` and `openlrLastLocationReferencePoint` are given by
coordinates (WGS-84), bearing and road class; the found route is trimmed by the offsets
`openlrPositiveOffset` and `openlrNegativeOffset` to the actual extent of the event. If two points are not
enough, intermediate points are used. For a point-like event, OpenLR describes a short section at the
place of the event (the offsets do not delimit a section of zero length).

=== Road chainage location referencing

Road chainage is described by the `linearWithinLinearElement` element whose `linearElement` carries the
road number (`roadNumber`). `directionRelativeOnLinearSection` specifies the direction relative to the
chainage (`aligned` along, `opposite` against it) and `fromPoint` and `toPoint` of type
`DistanceFromLinearElementStart` the distance of the start and end of the event from the beginning of the
road in metres (`distanceAlong`).

[[gn]]
=== Global Network location referencing

Sections of the Global Network road network (GN, ŘSD) are described as follows:

* Each section is one `linearWithinLinearElement` element whose `linearElement` is of type
  `LinearElementByCode`: `linearElementReferenceModel` = `CZ-RSD-GlobalNetwork`,
  `linearElementReferenceModelVersion` = network version and `linearElementIdentifier` = section
  identifier. All sections of the route are given in travel order, including full inner sections.
* `directionRelativeOnLinearSection` specifies the travel direction relative to the section coding, i.e.
  the direction in which the section was created in the GN database: `aligned` (along the coding),
  `opposite` (against the coding), `both` (the section serves both directions). The direction may
  alternate along a route so that the section ends connect – e.g. when the route passes a section created
  by coding another road that runs concurrently with it.
* One-way sections (e.g. separate carriageways, junction ramps) are always coded in the travel direction;
  they are therefore travelled only as `aligned` and a route never runs against them.
* `fromPoint` and `toPoint` are the points where the route enters and leaves the section, always of type
  `PercentageDistanceAlongLinearElement` – percent of the section length (0–100, at most 2 decimal places) measured from the start
  of the section coding. For `aligned` the value increases (e.g. 20 → 100), for `opposite` it decreases
  (e.g. 100 → 20); a full section is 0 → 100 or 100 → 0.
* The *start and end of the location* are given by the percentages of the first and last section. The GN
  sections do not carry the coordinates of the start and end; they are carried by the location path
  `gmlLineString` (<<prubeh>>).

A location valid for both directions of travel is described in the GN network as follows:

* If the sections serve both directions to the same extent, they are given once with
  `directionRelativeOnLinearSection` = `both`, in the order of the first direction and with its points:
  `fromPoint` → `toPoint` describes travel in the first direction, so a decreasing value (e.g. 100 → 30)
  means that the first direction runs against the section coding. The opposite direction is the same list
  read from the end, with the points in reverse order. Only sections passable in both directions may have
  direction `both`.
* If the opposite direction runs elsewhere (separate carriageways, one-way sections) or to a different
  extent, the whole route of the first direction is given first, followed by the whole route of the
  opposite direction, both as `linearWithinLinearElement`. The first direction runs from the start to the
  end of the location, the opposite direction from the end to the start. Each route is preceded by the XML
  comment `<!-- GN firstDirection -->` or `<!-- GN oppositeDirection -->` (model element names, independent
  of language). The comment is meant for human readers and a receiver should not rely on it; it determines
  the boundary between the routes from the connectivity of the sections in the GN network. Both directions
  are also described unambiguously by OpenLR (`firstDirection`, `oppositeDirection`).

[[prubeh]]
=== Location path

A linear location carries its path in WGS-84 in the `gmlLineString` element so that a subscriber can show
it on a map without the GN network, the ALERT-C location table or an OpenLR decoder:

* `posList` – "latitude longitude" pairs separated by spaces; `srsName` = `EPSG:4326`,
  `srsDimension` = `2`.
* The line runs in the direction of travel: the first point is the start and the last point the end
  of the location. It is
  made from the geometry of the GN sections trimmed by the percentages of the edge sections; the start and end
  are exact, intermediate points are simplified so that the line deviates from the section geometry by at
  most 10{nbsp}m. Coordinates have 5 decimal places (≈{nbsp}1{nbsp}m).
* For a bidirectional location the line runs in the first direction (the model allows one line per
  location).

[[skupiny]]
=== Area events and groups of sections

A phenomenon that affects several roads or non-contiguous sections (closure of an area, an event, a
calamity) is described by one record whose location is a group of sections:

* *One-off area* – `locationReference` of type `loc:LocationGroupByList`; the individual sections are in
  `locationContainedInGroup` elements (at least two), each described as a separate linear location
  (`loc:SingleRoadLinearLocation`) by all available methods.
* *Recurring area* (regular winter closures, permanent diversion routes) – reference to a predefined group
  of the `cz-ndic_d2-pls` format: `locationReference` of type `loc:LocationGroupByReference` with
  `predefinedLocationGroupReference` (`targetClass` = `loc:PredefinedLocationGroup`).

Area locations are not used; an area is covered by a list of linear sections.
